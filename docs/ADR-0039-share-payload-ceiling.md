# ADR-0039: 共有リンクペイロードのリソース上限

## 状態
実装済み (v1.7.97)

## 背景
`Share.importFromHash` は `z:` kind の URL fragment を `DecompressionStream` で
展開し、`JSON.parse` → `validShape` フィルタ → `confirm(importConfirm)` の順に
処理する。つまり **ユーザー確認より先に、リンクの展開・parse が実行される**。

deflate は圧縮率が高く、数 MB の圧縮済み fragment が数百 MB の JSON に展開
しうる。第三者が送ったリンクを開いただけでタブが数百 MB のテキスト生成と
JSON.parse に占有され、事実上フリーズする — 確認ダイアログにさえ到達しない
軽度のリソース枯渇経路だった。

## 決定
2 つの天井を設け、超過は既存の `invalidBoard` toast + ハッシュクリアで拒否
(ADR-0038 と同じ経路):

- `SHARE_MAX_BYTES = 128*1024*1024` — **展開後**の JSON 文字列長上限。
  parse 前に検査するのが要点 (展開コスト自体は Response.text() なので
  上限超過でもメモリに残るが parse コストを回避できる)。
- `SHARE_MAX_SHAPES = 200000` — parse 後の `data.shapes` 配列長上限。
  現実のボード (~10k 形状) から十分な余裕を持たせつつ、巨大配列の
  `clone`/`filter`/`_apply` ループを防ぐ。

`.board` ファイル取り込みはユーザー自身が選んだローカルファイルであり、
第三者の送りつけ経路ではないため対象外 (将来必要なら同じ定数を流用可)。

## 断念した代替案
- fragment の raw バイト数で制限する → 展開率が問題なので圧縮前サイズは
  無意味 (2MB 圧縮が 500MB に展開しうる)。
- 上限超過をサイレント無視 → ADR-0038 で統一した「toast + ハッシュクリア」
  に揃える方が一貫。
- 128MB をもっと小さく → 画像 dataURL を多数含む正当なエクスポートが
  数十 MB に届きうるため、実害ラインより十分上に設定。

## 影響
悪意ある/壊れた共有リンクを開いてもタブがフリーズせず、`invalidBoard`
トースト + URL クリアで安全に失敗する。正常なリンク・ファイル取り込みの
挙動は不変。
