# ADR-0019 — `peerId` はレプリカを識別する。ブラウザではない

- Status: Accepted (v1.7.86, 2026-09-02)
- 関連: ADR-0002 (per-property LWW)、ADR-0015 (複製される undo)、ADR-0018 (オフライン)
- 影響: **静かなデータ損失の修正**。ユーザーの操作が無言で消える経路を1本塞ぐ。

## Context

ADR-0018 で「オフラインの柱は誰もブラウザで確かめていなかった」ことが判明した。
同じ問いを同期の柱に向けた: **「同期は、誰がブラウザで確かめたのか?」**

`test.mjs` の2ピアテストは充実している。しかしそれらは**ハーネスが制御する fake channel**で
2つの eval 済みコピーを繋ぐもので、op ログが収束することは示すが、**実ブラウザの2つ目の
タブが何かを受け取ること**は示さない。BroadcastChannel・IndexedDB の起動時引き継ぎ・
RAF 駆動の再描画は、すべて fake の外側にある。

実 Chromium × 実 http オリジンで2タブを走らせ、**実バグを発見した**。

### 実測 (2026-09-02)

```
A peerId: f6cfcf15ac674b18b8751b63d1838c88
B peerId: f6cfcf15ac674b18b8751b63d1838c88
IDENTICAL: true

after A draws once:   A: shapes=1 seq=1 seen=[c941:1]
after B opens:        B: shapes=1 seq=0 seen=[]
after B draws:        A: shapes=1   ← 増えない
                      B: shapes=2
→ 盤面は恒久的に乖離。エラーは一切出ない。
```

## 何が壊れていたか

CRDT の重複排除キーは `op.clock.peer + ':' + op.clock.seq`。
このキーが一意であるためには、**識別子がレプリカ単位でなければならない**。

`PEER_ID` は `localStorage['board.peer']` から読まれ、コメントは
「**persistent per browser**」と書いていた。しかし:

> **同一ブラウザの2つのタブは、2つの独立したレプリカである。**
> 各々が自分の `state.seq` を 0 から数え、`seenOps` を空から積む。

識別子を共有した瞬間、両者の N 番目の op は**区別不能**になる。そして
`Store.commit()` は `_apply` の**前に** `seenOps` を検査する (index.html:1256):

```js
const k=op.clock.peer+':'+op.clock.seq;
if(state.seenOps.has(k))return;       // ← ここで返る。_apply は走らない
...
this._apply(op,true);
```

したがって衝突した側は「送信に失敗する」のではなく、**自分の編集を自分で捨てる**。
**ユーザーが図形を描いても、何も現れない。**

### 同じ欠陥は単一タブでも起きる

リロードすると `state.seq` は 0 に戻るが、永続化された `peerId` は変わらない。
WebRTC の相手ピアは旧 op を `seenOps` に覚えているため、**リロード後の編集は
`seq` が旧最大値を超えるまで全部捨てられる**。永続化はあらゆる場面で有害だった。

### なぜ検査をすり抜けたか

**理由1 — ハーネスが手で正解を与えていた。**
2ピアハーネスは冒頭で `A.state.peerId='peerA'; B.state.peerId='peerB';` と代入する。
**製品が破っていた当の性質を、ハーネスが親切心で供給していた。** ADR-0018 で学んだ
「ハーネスの穴は仕様ではない」の変奏で、今回は穴ではなく**過剰な親切**。

**理由2 — 存在検査がバグを不変条件として固定していた。**

```js
['PEER_ID persistence', html.includes("localStorage.getItem('board.peer')")],
```

この検査は**バグの実装を要求していた**。正しく直すと落ちる検査である。
存在検査が誤った設計を保護した3例目。

## Decision

**`PEER_ID` の永続化を削除する。** 4行を1行にする:

```js
const PEER_ID=uid();
```

**なぜ削除が正しいか (第一原理)**: 永続化が奉仕していた目的が無い。`peerId` の用途は

1. **op の重複排除** — レプリカ単位の一意性のみを要求し、永続性は要求しない。
   むしろ永続性が一意性を**破っていた**。
2. **スナップショット送信元の選出** (`state.peerId<msg.peer`) — 順序だけあればよい。
3. **アバターの頭2文字** — 装飾。

一方で永続化は上記2種の衝突を**生んでいた**。
「削除して10%戻さないなら削り足りない」の典型で、**4行が1行になり、バグが2つ消える**。

リロード後に別 ID になるのは**正しい**。それは実際に新しいレプリカである
(`seq` が 0 に戻り、`seenOps` が空になる)。旧エントリは `_reapPeers` が回収する。

## 却下した代替案

1. **永続 id + タブ別サフィックス** (`browserId + ':' + tabNonce`) — 一意性は回復するが、
   「ブラウザを跨いで同じ人だと分かる」という**誰も要求していない性質**のために
   複雑さを足す。用途 1〜3 のどれもそれを必要としない。
2. **`seq` をグローバル単調にする** (localStorage で共有) — タブ間で `seq` を奪い合う
   書き込み競合を生み、しかも**レプリカの独立性という CRDT の前提を壊す**。
   問題は `seq` ではなく `peer` にあるのに、`seq` を直そうとする典型的な誤診。
3. **`sessionStorage` に置く** — タブ単位にはなるが、同一タブのリロードでは残るため
   **リロード衝突は直らない**。半分しか直らない案。
4. **`seenOps` に `ts` も混ぜる** — キーを太らせて衝突確率を下げるだけで、
   同一性の欠陥そのものは残る。根本ではなく症状への対処。

## 既知の限界

1. **リロードごとにアバターの頭2文字が変わる。** 装飾であり、かつ「新しいレプリカである」
   という事実の正直な反映でもある。
2. **旧 `localStorage['board.peer']` は掃除しない。** 読まれなくなるだけで害はなく、
   削除コードを足せばそれ自体が保守対象になる (「削除したものは保守しなくていい」)。
3. **`seenOps` の増加**: レプリカが増えれば異なる id が増えるが、`MAX_SEEN_OPS` で
   上限が効いており、既存の trim 経路がそのまま働く。

## 検証

`sync-browser.mjs` (新規、依存ゼロ、`a11y-browser.mjs` / `offline-browser.mjs` の兄弟)。
**実 Chromium の2タブ**で結果を見る (計12検査):

- 2タブが**異なるレプリカ id** を持つこと (根本原因の直接固定)
- IndexedDB による起動時引き継ぎ
- **A→B と B→A の双方向**の即時伝播 (後者が壊れていた方向)
- **ADR-0015 の複製 undo** が相手タブで反映されること
- **リロード後の編集も相手に届く**こと (単一タブ版の同じ欠陥)
- 最後に**両タブが同一の盤面**を持つこと (件数ではなく内容で比較)

**非空虚性**: `git stash push index.html` で修正前ビルドに当てると **12中4が落ちる**。

`test.mjs` 側には、**修正の理由そのもの**を固定する振る舞いテストを追加した:
共有 id では B が自分の描画を自分で捨て、両盤面から消えること / 異なる id なら同じ2つの
commit が両方生き残ること。ハーネスが手で `peerA`/`peerB` を代入していた事実も
コメントに明記し、同じ隠蔽が再発しないようにした。

## 学び

**ハーネスが被試験体に親切をすると、その親切の分だけ検査は嘘になる。**
`peerId` を手で振り分けたのは「テストを書きやすくするため」だったが、それは同時に
「この性質は製品が保証している」という**検証されていない仮定**の注入だった。
ADR-0018 の「ソースを見る検査は結果を見る検査に負ける」と対になる教訓で、
**7例目**の「主張が実態を上回る」事例。
