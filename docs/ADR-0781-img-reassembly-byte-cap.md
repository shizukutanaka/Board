# ADR-0781 — img 再組立ての中間バイト上限

- 日付: 2026-09-29
- 状態: 実装済み

## Context

`k:'img'` 受信は chunk ごとに ≤96KB・`n` ≤4096・`seq` 範囲を検証し、
結合結果を `_imgIn` へ格納する直前に ≤12MB を判定していた — **全パーツ到着後**。
96KB × 4096 で宣言どおりのストリームなら ~384MB が `_imgChunks` スロットに
蓄積し得た (64 スロット・LRU で bounded だが桁が違う)。

ADR-0379 のチャンクキャップは「wire form の 12MB チェックは全パーツ後に走る」
ことを前提にしていたが、中間状態の累積量には何もかかっていなかった。

## Decision

スロットに組立バイト数 `st.b` を持たせ、新規パーツ格納ごとに加算:

```js
if(!st.p[seq]){st.p[seq]=msg.data;st.g++;st.b=(st.b||0)+_ln(msg.data)}
if(st.b>12_000_000){this._imgChunks.delete(msg.key);break}
```

結合結果の上限と同じ 12MB で**到着中に**打ち切る — 正当なストリームは結合時に
同じキャップで棄却されるので、早い時点で捨てても意味は同じ。

## Consequences

- 1 スロットの保持量が 12MB で頭打ち (理論上の 384MB → 12MB)。
- 中断後に残りの seq が届くと新スロットとして再開する (out-of-order 再組立ての
  従来セマンティクスを保持 — バイトカウンタはリセットされる)。
- 通常の画像 (≤12MB 結合) の挙動は不変。
- テストピン3件: abort → 新スロット再開・バイトカウンタリセット・正常流不変。
