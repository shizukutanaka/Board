# ADR-0654: 空間グリッドの密度適応セルサイズ

## Context

空間索引 (ADR-0016/0032) は固定 200-unit 一様ハッシュ (`_GCELL`)。research-improvements.md は
「>500 shape で quadtree」を残課題としていたが、根本の問題はセル溢れ:

- **密な盤面** (数百図形が狭い領域に集中 — インポートした drawio、細密スケッチ): 1 セルに
  数百図形が入り、`_queryGrid`/`_gridRectCandidates` がセル内 O(n) 走査に退行。
- **疎な盤面** (少数図形が広い領域に散布): 問い合わせが不要なセル列を走査する。

完全な quadtree (階層分割・節点管理) は ~150 行規模で、単一ファイルのコード量に対し収益が
薄い。代わりに **1 レベルの quadtree 細分化に相当する適応セルサイズ** を採る。

## Decision

`_buildGrid` が盤面 bbox と図形数からセルサイズを決定し、返却 `grid.cs` に格納:

```js
let cs=_GCELL;
if(_ln(shapes)>64){
  const ab=_bA(shapes);
  if(ab)cs=_max(48,_min(960,_rnd(_sqr(ab.w*ab.h/_ln(shapes))*2)||_GCELL));
}
```

- `sqrt(A/n)` ≈ 平均図形間隔 — その 2 倍をセル幅とする (1 セルあたり ~4 図形が期待値)。
- クランプ [48, 960]: 下限は stroke overshoot / ヒットテストの余白 (~20u) の 2 倍を確保、
  上限は rect 問い合わせのセル走査数を抑制。
- ≤64 図形では既定 200 を維持 (小盤面で適応コストを払わない — 既存挙動と完全一致)。
- `big` 判定 (>8 セル幅) はセル数基準のまま — セルサイズが変わっても同じ規則。
- クエリ 2 関数は `grid.cs || _GCELL` でフォールバック (旧形グリッド互換)。

グリッドは `_gridVer` で再構築されるため、盤面の密度変化に追従して自動的に再適応する。

## Consequences

- 密盤面 (例: 200 図形を 80x80 領域に集中): cs≈48、セル当たり ~17 図形 → hover/binding の
  候補走査が ~10x 縮小。
- 疎盤面 (例: 100 図形を 20000² に散布): cs≈960、rect 問い合わせのセル走査 ~5x 縮小。
- 標準盤面 (≤64 図形または通常密度): cs=200 で従来と同一。
- 完全 quadtree の階層管理コストを回避 — 差分 ~+250B。
