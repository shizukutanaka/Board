# ADR-0603: 受信結合上限を超えるフラグメントストリームの送信側警告 + 受信側明示棄却

## 状態
実装済 (v1.7.630)

## 背景
`_fragSend` は巨大メッセージ (`snap`/`opc`) を 64KB フラグメントへ分割し、
`_fragIn` が `n` チャンクを再結合する。受信側の結合上限は **n ≤ 384**
(384×64KB ≈ 24MB) — DoS ガードとして意図的。

2つの不整合があった:

1. **送信側の無警告送出**: `_fragSend` は `n` を無制限に生成するため、
   >24MB の op (例: 20万図形の一括削除 ≈30MB) を送出しても、全受信者は
   n>384 を n=1 として解釈し、先頭 64KB フラグメントだけを「完成形」として
   `_JP` へ投げ、パース失敗で無通知棄却する。送信者は自分の変更が
   同期されなかったことに**永遠に気づかない**。
2. **受信側の偽1チャンク結合**: `n>384` が n=1 にフォールバックする設計は
   「最初のフラグメント=完全メッセージ」と誤読し、64KB 切り詰め JSON を
   パースへ送る無駄な経路を持っていた (棄却はされるが迂遠)。

## 決定
- 送信側: `_fragSend` で `n>384` の場合は送信せず `syncTooLarge` トーストを
  表示 (ja/en 追加)。ユーザは「分割して再実行」すれば op が届く。
- 受信側: `_fragIn` で宣言 `n>384` をアセンブリ開始前に明示 `return`。
  n=1 フォールバック経路は廃止せず残置 (非数値 n の整合は既存動作)。

## 影響
- 巨大 op の「届かないが誰も知らない」分岐ケースを、送信者への
  可視通知に転換
- 悪意ある n 宣言の受信処理コストがゼロに
- ADR-0602 (op 配列上限を盤面上限へ) と合わせて、op サイズ系の
  無通知棄却経路を全て閉じた
