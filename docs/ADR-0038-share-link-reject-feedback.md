# ADR-0038: 共有リンク拒否経路のフィードバック統一

## 状態
実装済み (v1.7.96)

## 背景
`Share.importFromHash` の失敗経路は非対称だった:

- 暗号化リンクの鍵欠落/誤鍵/非セキュアコンテキスト → **toast + ハッシュクリア** (v1.7.77)
- デコード/展開/JSON.parse の例外 → **toast のみ** (`invalidBoard`)、ハッシュ残留
- 未知の kind (`#b=x:…`)、`shapes` が非配列の JSON、全形状が `validShape` 不通
  → **無言で `return false`**、ハッシュも残留

破損・改竄されたリンクでは、ユーザーは何も起きないボードを見ながら、
アドレスバーに悪い URL が残り続けた (リロードしても同じ無言失敗が繰り返される)。

## 決定
- `clearHash` ヘルパーを `e:` 分岐から関数先頭へホイストし全失敗経路で共有。
- 3 箇所の無言 `return false` を `UI.toast(t('invalidBoard'),'err');clearHash();return false` に。
- 既存の `catch` (decode/parse 失敗) でも `clearHash()` を追加 — 壊れたリンクを
  アドレスバーに残さない。

`confirm(t('importConfirm'))` でユーザー自身がキャンセルした場合のみ、従来どおり
ハッシュを残す (再読み込みで再試行できる設計を維持)。

## 断念した代替案
- 無言失敗を「そのままの挙動」と割り切る → 鍵経路では既に toast+clear していた
  ので一貫性がなく、壊れたリンクのサイレント失敗はデバッグ不能。
- `invalidBoard` ではなく `shareBadKey` を使い回す → 鍵不一致とペイロード破損は
  原因が異なるため既存の `invalidBoard` が適切。

## 影響
壊れた/改竄された共有リンクで、ユーザは「ボードファイルが無効です」の
フィードバックを得、URL もクリーンになる。正常なリンク・利用者キャンセルの
挙動は不変。
