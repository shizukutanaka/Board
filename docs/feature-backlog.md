これは `docs/feature-triage-2026-07.md` (ソクラテス式問答による過不足分析、人間向けの
判断記録) の結論をチケット化したものである。**このファイル単独で読んで、前提知識なしに
次の一手が分かる**ことを目的とする。対象コードは `/home/user/Board/index.html` (単一
ファイル、Board — オフライン優先ホワイトボード)。行番号は編集のたびにズレるため使わず、
すべて grep 可能なシンボル名で参照する。判定基準は CLAUDE.md の製品判断: Board は
「速い・私的・使い捨ての単独スケッチ (scratchpad)」— multipage/複数ボード・identity 前提の

各チケットのフィールド: **Verdict** (`KEEP`=変更不要の記録 / `CUT`=削除・簡素化候補 /
`FIX`=実装すべき不足) / **Evidence** (該当シンボル、実在確認済み) / **Action** (次の一手) /
**Effort** (S/M/L) / **Depends on**。

## FT-06 — long-press でコンテキストメニューを開く (P1、最優先) — ✅ 実装済み (v1.7.55, ADR-0006)
- Verdict: `FIX`
- Evidence: コンテキストメニューの唯一の開始点は
  `canvas.addEventListener('contextmenu',e=>{e.preventDefault();UI.openCtxMenu(e.clientX,e.clientY)})`。
  メニュー本体は `UI.openCtxMenu(x,y)`。メインの単一ポインタジェスチャーは
  `canvas.addEventListener('pointerdown',e=>{...})` (bubble-phase、`Presentation.isActive()`
  チェックの直後の handler)。タッチ由来かどうかの判定は現状コードに一切存在しない
  (`pointerType` の使用箇所は 0 件)。iOS Safari 等は canvas 上の long-press から
  `contextmenu` を確実に発火しないため、タッチ端末ではメニュー全体が事実上開けない。
- Action: 上記の pointerdown handler 内で `e.pointerType==='touch'` の場合に ~500ms の
  タイマーを開始する。タイマー発火までに一定距離(数px)以上ポインタが動くか、pointerup/
  pointercancel が先に来たらタイマーを cancel する(通常の描画・ドラッグと衝突しないため)。
  タイマー発火時に `UI.openCtxMenu(e.clientX, e.clientY)` を呼び、以降のジェスチャー
  (描画開始等)を抑制する。
- Effort: S — タイマー1本 + キャンセル条件のみ。既存の `UI.openCtxMenu` をそのまま再利用。
- Depends on: none
- 効果: この1件で `ctxAlign*` (整列)、`doClearAll`/`ctxClear` (全消去)、
  `ctxCopyStyle`/`ctxPasteStyle` (スタイル転写)、複製・コピー・ペースト・削除・全選択・
  グループ化・z順序・フリップ・ロックがすべてタッチ到達可能になる。

## FT-20 — WebRTC 接続失敗時のユーザーフィードバック欠如(第4弾, v1.7.68 後の未監査領域レビューで発見) — ✅ 実装済み (v1.7.76)
- Verdict: `FIX`(ただし実ブラウザ検証が前提 — このセッションでは実装しない)
- Evidence: `Net._wireDC` の `dc.onclose` は接続の切断を `t('disconnected')` でトースト
  するが、これは**一度 open した DataChannel が閉じたとき**しか発火しない。手動
  シグナリングの WebRTC は NAT/ファイアウォール越えの失敗で**そもそも open しない**

  `RTCPeerConnection` には `onconnectionstatechange`/`oniceconnectionstatechange`
  ハンドラが無いため、ユーザーはトークンを交換した後**無反応のまま待ち続ける**。
- Action: `_wrtcInit` で `onconnectionstatechange` を配線し `connectionState==='failed'`
  で失敗トーストを出す。ただし「一度も open しなかった / open 後に failed / 正常 close」
  の3ケースで**二重トースト・トースト欠落**が起きないよう `dc.onclose` との協調が要り、
  その分岐挙動は実ブラウザの RTC 状態機械のタイミングに依存する。**fake-DOM テスト
  ハーネスは `RTCPeerConnection` を `undefined` としてスタブしており、この状態遷移を
  検証できない**ため、FT-13(dirty-rect)と同じく実ブラウザでの目視/自動検証手段が
  確保できてから着手する。盲目実装は 1617 pass の成熟コードベースに検証不能な回帰を
  持ち込むリスクがある。
- Effort: S(コードは小さい)/ ただし検証手段の確保が前提
- Depends on: 実ブラウザでの WebRTC 接続テスト手段(このセッションには無い)

**実ブラウザ検証が確保できるまで着手しない**と決めていた。しかしそれは*問題*の性質ではなく
*ハーネス*の性質であり、外せる制約だった。実際に必要だったのは実ブラウザではなく、

(e) 応答側の対称性 の5経路すべてを決定的に検証できた。

それとも「描画コマンド列の等価性」で足りるのかは、着手前に問い直す価値がある
(ただし dirty-rect はレンダーループの再設計であり、FT-20 とはリスクの桁が違う)。

残る未着手はブロック中の FT-09/10/11/13/15 のみ。

# 要件監査 (v1.7.79) — イーロン・マスクの5段階アルゴリズム

> 1. すべての要件を疑え(要件には**部署ではなく人名**が付いていなければならない)
> 2. **部品や工程を削除せよ**(削除したものの1割以上を戻していないなら、削除が足りない)
> 3. 単純化・最適化せよ — **ただし2の後で**(最もよくある誤りは、存在すべきでないものを最適化すること)
> 4. サイクルタイムを短縮せよ
> 5. 自動化せよ — **最後に**

このプロジェクトは長らく 3 と 5 ばかりやり、**2 を一度もやっていなかった**。以下は 1 と 2 の実施記録。

## 削除した要件

### ❌ FT-13 (dirty-rect) / FT-14 (quadtree 拡張) / spec §14.3 の「空間索引」行
**根拠: 実測**。3つとも「>2000 図形で線形処理が重い」という**誰も測っていない主張**に乗っていた
(本 backlog 自身が「『描画が重い』という実測の証拠が無い」と書いていた)。

| 図形数 | draw() 走査 | pickTop |
|---|---|---|
| 500 | 0.48ms | 0.076ms |
| 2,000 | 0.21ms | 0.038ms |
| 10,000 | **0.88ms** | 0.108ms |

**10,000 図形(主張の閾値の5倍)で 1ms 未満**。しかも**盤面サイズに比例しない** —
2,000 が 500 より速いのは、viewport カリングが既にコストを「画面に写っているもの」で
縛っているから。**quadtree も dirty-rect も、存在すべきでない要件だった**。
作らずに削除し、`test.mjs` の perf ガード1本に置き換えた(超線形化したら落ちる =
証拠付きで要件が復活する)。**3つのロードマップ項目が assertion 1本になった。**

### ❌ FT-10 (axe-core による自動 a11y 監査)
要件が**目的ではなく手段**を指定していた。「axe-core を動かす」は手段で、目的は
「a11y が実際に機能すること」。その目的には既に (a) 依存ゼロの静的検証
(`docs/a11y-audit-2026-07.md`)、(b) DOM ミラー (ADR-0016) が当たっており、
残る本命は**実機スクリーンリーダー確認 (FT-11)** — これは axe-core では代替できない。
加えて npm 依存の導入は本プロダクト第一の不変条件(外部依存ゼロ)と反りが合わない。
**手段を指定した要件を削除し、目的 (FT-11) だけ残す。**

## 前提が誤っていた要件

### ⚠️ FT-09 (CI ワークフロー)
「ファイルは v1.7.58 で作成済み、`.gitignore` が `.github/` を除外しているので未コミット」と
記録されていたが、**`.github/` はリポジトリにもローカルにも存在しない**。過去セッションの
使い捨てコンテナ内で作られ、そのまま消えている。CLAUDE.md の MAP も「作成済み」と
書いており、**実態と食い違う記述**だった(v1.7.71/72 が正したのと同種の誤り)。記述を訂正。
なお CI は**5段階アルゴリズムの「自動化」= 最後**にあたる。CI が守る不変条件
(test / 構文 / innerHTML / 外部リソース / サイズ)は**すべて `node test.mjs` が既に実行**
しており、自動化は 1〜4 を終えてから着手する。

## 残す要件(証拠あり・目的が明確)

- **FT-11 実機スクリーンリーダー確認** — 人間の手が要る。ADR-0016 が保証するのは
  「正しいマークアップが DOM に存在すること」までで、実際の読み上げは別。
- **FT-15 画像 dataURL の参照分離** — ただし要件を**目的で書き直すべき**:
  「dataURL を分離する」(手段)ではなく「大きな画像で保存・共有が壊れないこと」(目的)。
  現状 4MB 上限があり、実害の測定はまだ無い。**測ってから決める** — FT-13 と同じ轍を踏まない。


## 第4・第5段階の結果 (v1.7.80)

### 4. サイクルタイム短縮 — **やることが無かった(実測)**
`node test.mjs` = **2.2秒**、`node coverage.mjs` = **3.5秒**。編集→検証のループが2秒なら
ボトルネックではない。ここを最適化するのは、まさに FT-13 で削除したのと同じ誤り
(存在しない問題の最適化)。**測って、何もしないことを選んだ。**

### 5. 自動化 — CI を追加 (最後に、かつ最小限)
`.github/workflows/ci.yml` を追加。**検査を一切再実装しない** — 単一ファイル性・
外部オリジン禁止・innerHTML 禁止・サイズバッジの正直さ・1600超の振る舞い検査は
すべて既に `test.mjs` にあり、CI は `node test.mjs` と `node coverage.mjs --max=139` を
走らせるだけ。CI に検査を書き写せば真実の源が2つになり、必ず食い違う。

**`.gitignore` の `.github/` 除外について — 試した結果、前提は正しかった**。
「push に workflows 権限が要る」という理由は長年**検証されていなかった**ので、
v1.7.80 で実際に push してみた。結果:

```
! [remote rejected] refusing to allow a GitHub App to create or update workflow
  `.github/workflows/ci.yml` without `workflows` permission
```

**ブロックは実在した。** 除外を元に戻し、CI 定義は `docs/ci-workflow.yml` に置いた
(冒頭に有効化手順。人間が30秒でコピーできる)。

FT-20 では同種の未検証の前提が**誤り**だったが、今回は**正しかった** — どちらも

方法であって、前提が必ず間違っているわけではない。**

### FT-15 — 要件を目的で書き直して解決 (v1.7.80)
当初の要件は手段(「dataURL を別ストアに分離する」、Effort: L)を指定していた。
目的で書き直すと「**大きな画像で共有が壊れないこと**」。実測:

| 画像 | 共有 URL | Chrome の実用上限比 |
|---|---|---|
| 0.5MB | 686k 文字 | **21倍** |
| 4MB (アプリ上限) | 5,485k 文字 | **171倍** |

**dataURL を分離しても解決しない** — 盤面は URL に乗って運ばれるので、バイトは結局移動する。
本当の欠陥は「**使えないリンクを黙って手渡していた**」こと。`SHARE_URL_MAX=16384` を超えたら
共有モーダルで警告し、`.board` 書き出しを案内する。**Effort L の設計が、閾値1つで済んだ。**


## 機能面の削除は「しない」と決めた (v1.7.81) — 第2段階の較正

第2段階は「削除せよ」であると同時に「**戻すことになるものを削除するな**」でもある
(「削除したものの1割以上を戻していないなら削除が足りない」は**較正**のテストであって、
壊れるまで切れという指示ではない)。scratchpad という製品の正体に照らして
プレゼンモード等を疑い、実測した:

| 機能 | サイズ | script 比 |
|---|---|---|
| プレゼンモード + レーザー | ~9.9KB | 3.9% |
| ミニマップ | ~4.7KB | 1.8% |
| シェイプ検索 (⌘F) | ~1.2KB | 0.5% |
| スケッチ整形 (ADR-0005) | ~2.2KB | 0.9% |
| コネクタラベル (ADR-0003) | ~0.4KB | 0.2% |

**合計 18.4KB = script の 7.3%**。そして**サイズは制約ではない**(中央値ページの 1/30、
コメント削除の項で確認済み)。全機能が ADR を持ち、テストされ、出荷済み。
「戻すことになるか?」— **なる**。よって**削除しない**。

**削除の材料が尽きたことこそ第2段階の結果**である。295KB のコードから静的解析で
見つかった死コードは定数1つだけ、機能は全て正当化済み、重かったのは**要件と工程**の側
(ロードマップ3項目・監査要件1項目・配点表)で、そちらは削除した。
スローガンを満たすために動く機能を切るのは、削除のための削除にあたる。
