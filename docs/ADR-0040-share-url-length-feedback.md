# ADR-0040: 共有リンクの長さ警告と生成失敗フィードバック

## 状態
実装済み (v1.7.98)

## 背景
Share モーダルには2つのフィードバック欠落があった:

1. **`Share.exportToUrl` の失敗が握り潰される** — `refresh()` の `.catch(()=>{})`
   が reject を丸呑みし、URL フィールドに前回の古い値(あるいは空)が残る。
   ユーザーは壊れたリンクをコピーして送りつけることになる。
2. **URL 長の上限を知らせない** — fragment 埋め込みリンクはボードが大きくなると
   容易に数万文字を超え、ブラウザ自体は耐えてもチャットアプリ(LINE/Slack/
   メールの自動リンク化)が長い URL を切り詰める。受け取った側は壊れたリンクで
   `invalidBoard` になるだけで、送った側には何の手がかりもない。

## 決定
- `SHARE_URL_WARN = 32768` を新設: 生成された URL がこれを超えたら
  `#shareWarnLong` (data-t で ja/en) を表示し、「大きい盤面は .board
  エクスポート (⌘⇧E) の方が確実」と代替経路を提示する。
- `exportToUrl` の reject で `shareUrl.value=''` (古いリンクを残さない) +
  `shareWarnLong` を隠す + `UI.toast(t('shareExportFailed'),'err')`。

32KB の根拠: 一般的なチャットの自動リンク化は数百〜数千文字で不安定になるが、
警告の目的は「明らかに危険なサイズ」で早めに気づかせること — 32KB は
実害ラインより十分余裕を持ちつつ、正常盤面 (数 KB) では絶対に出ない。

## 断念した代替案
- URL 長をコピー時にブロックする → ブラウザ直送なら長くても動くケースがある。
  警告に留めて判断はユーザーに委ねる。
- 暗号化時だけ閾値を変える → 鍵分は ~60 文字の差でしかなく、単一閾値で十分。
- `shareExportFailed` をモーダル内の赤文字にする → toast が既存の失敗通知の
  一貫した経路 (invalidBoard/saveFailed と同じ)。

## 影響
- 生成失敗時: 古い URL をコピーする事故が消え、エラートーストが出る。
- 大きい盤面: ユーザーは送信前に「.board が確実」と知る — 相手側の
  `invalidBoard` 困惑を未然に防ぐ。
- 小さい盤面 (大多数): 挙動不変 (警告は出ない)。
