# ADR-0021 — 画像キャッシュの O(1) フィンガープリントキー

- Status: Accepted
- Date: 2026-09-23
- 関連: ADR-0018 (ペン bitmap)、ADR-0019 (同じ「毎フレームの隠れた大コスト」)

## 問題

`_imgCache` は `Map<dataUrl, Image>` — dataURL 本体をそのままキーにしていた。
Map のキー照合は文字列全体をハッシュするため、**4MB 級の dataURL を
フレーム毎に読み切る**コストが生じていた (メイン canvas + ミニマップの双方で
画像ごとに 1 回/フレーム)。10 枚の大画像が見えているだけで
30MB+/frame の文字列スキャン = 数 ms。

## 決定

`_imgKey(u) = mimeヘッド(5..32) + ':' + バイト長 + ':' + 末尾64文字`
をキーに使う。誤一致には mimeヘッド・バイト長・末尾64base64文字の同時一致が
要るため、同一ボード内での自然発生は実用上無視できる (仮に起きても影響は
キャッシュ画像の誤表示のみで、キーが認証的意味を持たないため欺瞞の経路に
はならない)。コストは入力長に依らず一定 (~100 chars)。

キャッシュの LRU セマンティクス (`_imgCache`, `IMG_CACHE_MAX`, 最古退避) は
一切変更しない — キーの生成方法のみ。

## 却下した案

- **WeakMap<shape, Image>**: shape 参照キーはハッシュコストゼロで最も速いが、
  同一 dataURL を持つ複数シェイプが個別にデコードされメモリ倍増。
  dedup 効果を残すため不採用。
- **shape.id キー**: `state.shapes` のオブジェクトは Store が in-place
  mutate するので id は安定だが、同一画像の重複ペーストで共有できない点は
  同上。さらに dataURL のみを持つ呼び出し経路 (将来的な pre-decode 等) と
  相性が悪い。

## 検証

- `node test.mjs` 全緑: `_imgKey` の決定性・head/len/tail での単射性・
  出力サイズの上限アサート
- 実ブラウザで画像ボードのフレームにキー計算コストが固定化されることを確認
