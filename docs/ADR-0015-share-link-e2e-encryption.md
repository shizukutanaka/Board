# ADR-0015: 共有リンクの E2E 暗号化 (FT-21)

- ステータス: 採用 (実装済)
- 日付: 2026-09-23
- 対象: `Share.exportToUrl` / `Share.importFromHash`、Share モーダル

## 背景

`CLAUDE.md` WHY の第4柱は「プライバシー・E2E」。しかし v1.7.71 の First-Principles
監査で判明した通り、共有リンク (`#b=z:` / `#b=j:`) は **deflate + base64 の平文**で
あり、リンクを知る第三者は鍵なしで盤面全文を復元できる。README の競合比較表の E2E 欄も
「✗ (未実装 — 計画中)」と正直に修正された。FT-21 はこの構造的ギャップを閉じる。

## 先例の調査

- **Excalidraw**: `https://excalidraw.com/#json=<scene-id>,<key>` —
  AES-GCM で暗号化し、**鍵を URL フラグメント内に配置**。フラグメントは HTTP
  リクエストに含まれないためサーバーは鍵を見ない (plus.excalidraw.com/blog/end-to-end-encryption)。
  コラボ用は `#room=<room-id>,<room-key>` で同じ構造。
- **ゼロナレッジ系ファイル共有** (fileshot 等): 同じく `#<AES_KEY>` をフラグメントに配置。
  AES-256-GCM + 12 byte ランダム IV が典型的。
- **MDN / NIST SP 800-38D**: AES-GCM は認証付き暗号 (AEAD) であり、CTR/CBC と違い
  改竄検知が内蔵。手動実装ミスの余地がない点でブラウザ暗号の第一選択。

## 決定

### ワイヤ形式

```
index.html#b=e:<base64url(iv ‖ ciphertext)>&k=<base64url(key)>
```

- `iv` = 12 byte 乱数 (`crypto.getRandomValues`) を暗号文先頭に連結。
- `k` = エクスポートした AES-256-GCM **256bit** 鍵の生バイト列。
- `additionalData = 'board:e1'` で暗号文をこの形式バージョンに束縛 (format-confusion 防止)。

鍵はフラグメント内にあるため、(a) `file://` 直開きではそもそも送信が発生しない、
(b) https で配られた場合もリクエスト/Referer に載らない — どちらでも E2E が成立する。

### 暗号化の内側は既存ペイロード

`e:` は「既存の `z:` / `j:` ペイロード文字列全体」を UTF-8 で暗号化したもの。
復号後に得た `z:…` / `j:…` を既存のデコード switch にそのまま流す。

- **圧縮→暗号の順序**: 暗号文は圧縮不能なので圧縮が先 (FT-21 設計論点 d)。
  ペイロードを内側に包むため、将来内部形式が変わっても `e:` は無条件に追随する。
- 旧 `z:` / `j:` リンクのインポートは**変更なしで継続動作** (設計論点 a: 後方互換)。

### UX

- Share モーダルに「🔒 暗号化リンク (推奨)」チェックボックスを追加。
  `crypto.subtle` が使える場合 **既定 ON**、使えない場合は無効化して平文のみ。
- 平文時は従来の警告 (`shareUrlWarn`) を維持。暗号時は「鍵はリンク内に含まれ、
  リンクを知る人だけが開けます」という注記に切替 (`shareUrlNoteEnc`)。
- チェックボックスの切替で URL を即時再生成。

### セキュアコンテキスト問題 (設計論点 c)

`crypto.subtle` はセキュアコンテキスト限定。`file://` は Chrome/Firefox で
potentially trustworthy として扱われるため、Board の主要経路 (file:// 直開き、
SW キャッシュの PWA) では問題なく動作する。`http://` 非 localhost で配られた
受信側は復号できない → 生成側で `crypto.subtle` 非検出時は自動的に平文リンクに
フォールバック + 従来警告を表示 (静かに暗号化を諦めるのではなく UI で明示)。

### エラー UX (設計論点 b)

| 状態 | 動作 |
|---|---|
| `e:` で `k` 欠落 | `shareNoKey` toast (err) + ハッシュ除去 |
| `crypto.subtle` なし | `shareNoCrypto` toast (err) + ハッシュ除去 |
| 復号失敗 (鍵違い/破損) | `shareBadKey` toast (err) + ハッシュ除去 |

失敗時にも `history.replaceState` でハッシュを除去する: 壊れたリンクの再読み込みで
同じエラーがループするのを防ぎ、鍵がアドレスバーに残らないようにする。

## 却下した代替案

- **鍵を別チャネルで送る** (ユーザーが手で鍵を共有): 鍵配布 UX が壊滅的に悪化。
  リンク1本で開ける利便性を捨てる価値はない。
- **AES-GCM-128** (Excalidraw 準拠): 十分安全だが 256 にしても API は同一・
  コスト増なし。採用理由がない。
- **`?` クエリや `location.pathname` 経路での鍵配置**: サーバーへ鍵が漏れ得る。
- **パスワード由来鍵 (PBKDF2)**: オプションとしては有用だが、既定で別途パスワード
  入力を要求すると「0秒で使い始める」に反する。将来の拡張余地として残す。

## 影響

- 後方互換: 既存リンクはそのまま開ける。`z:`/`j:` エクスポートも残る (opt-out)。
- セキュリティ: リンク自体が資格情報になる性質は変わらない (鍵がリンク内のため、
  リンクを持つ人は全員読める)。「転送経路での盗聴/サーバーへの漏洩」を防ぐのが
  本変更の効果であり、リンク管理の注意は引き続き必要 — README のセキュリティ節を更新。
- サイズ: 実装 + i18n + UI で raw +~3KB。512KB 上限内に十分収まる。
