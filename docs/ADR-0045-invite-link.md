# ADR-0045: 招待リンク — `#s=<offer>` で受け手の手順を一段減らす

- 日付: 2026-09-23
- 状態: 承認
- 関連: ADR-0008 (Share モーダル明確化), ADR-0017 (WebRTC 失敗フィードバック),
  spec.md §14.2「同期の運用性 **[P2]**」

## 背景

手動シグナリングは 4 回の copy/paste を要する:

1. 誘う側: 招待コード作成 → コピー → 送信
2. 受け手: 招待コードを貼り付け → 応答コード作成 → コピー → 送り返し
3. 誘う側: 応答コードを貼り付け → 接続

サーバ無しの制約上「URL を開くだけで共同編集」には原理的に届かないが、
**受け手の手順1 (貼り付け)** は URL にオファーを埋め込めば省略できる。
SDP オファーは ~1-2KB なので `#b=` 盤面共有リンクと違ってサイズ問題もない。

## 決定

- **誘う側**: 招待行に「招待リンクをコピー」ボタン (`rtcInviteLinkBtn`) を追加。
  `location.origin+location.pathname+'#s='+encodeURIComponent(rtcOffer.value)` をコピー。
  招待コード未作成なら `inviteLinkNoCode` トースト。
- **受け手**: `Share.inviteFromHash()` が起動時に `#s=` を検出したら
  Share モーダルを開き `rtcOfferIn` にコードを充填 + ハッシュ消去 +
  `inviteLinkOpened` トースト。
- **自動接続はしない**: リンクを開いただけで RTCPeerConnection が相手ホストに
  IP を晒すのはプライバシー上不可 (盤面共有の confirm プロンプトと同じ考え方)。
  「応答コード作成」のクリックは依然必須 — 省くのは貼り付け1回のみ。

## 断念した代替案

- **オファーと盤面を同梱 (`#b=…&s=…`)**: 盤面リンクと招待リンクの両方を持つ
  招待なら盤面が届いてからの接続もできるが、URL が巨大化し、既存の `#b` パーサを
  複合キー対応に広げるコストに見合わない。別キーに分離。
- **応答コードの URL 化 (受け手→誘う側の往復もリンク化)**: 応答側も `#a=` リンク
  を作れるが、誘う側は既に Share モーダルを開いて待っているので価値が薄い。見送り。
- **QR コード**: 既に議論済み・依存ゼロ制約で対象外 (FT-系トリアージ参照)。

## 影響

- i18n: `shareCopyInviteLink` / `inviteLinkOpened` / `inviteLinkNoCode` (ja+en)
- test.mjs: presence checks (ボタン/ハッシュ処理/エクスポート) を追加
- 構造上の制約は不変: 接続確立には相手側の応答ペーストが依然必要。
