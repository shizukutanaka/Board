# ADR-0011 — ピア選択ハイライト (presence: 他者の選択状態)

- Status: Accepted (implemented)
- Date: 2026-07-11
- 関連: ADR-0010(ピアカーソル — 本 ADR はその明示的な続き)、`docs/spec.md` §14.3
  ロードマップ「P2 | 選択ハイライト」、`docs/feature-backlog.md` FT-12

## なぜ (Context)

ADR-0010 は「他者カーソル」のみをスコープにし、「他者の選択状態のハイライト」を
別 ADR に明示的に切り出した。カーソルは「相手が今どこを指しているか」を伝えるが、
「相手がどの図形を編集しようとしているか」は伝えない — 同じ図形を同時に触って
LWW で片方の変更が上書きされる(ADR-0002 の収束は保証されるが意図の衝突は防げない)
事故は、選択の可視化で編集前に回避できる。Yjs の awareness プロトコルや主要エディタの
実装(カーソル+選択+メタデータを非永続メッセージで随時配信)とも同型の、確立された
パターンである。

ADR-0010 が持ち越した3つの設計論点(`docs/feature-backlog.md` FT-12)に本 ADR で
結論を出す。

## 何を (Decision)

### プロトコル: 新規メッセージ種別 `{k:'selection', peer, ids}`

- **非永続・op-log 対象外**(ADR-0010 と同じ): `state.peers` の各エントリに `sel`
  (id 配列)として保持するのみ。`Persist`/history/undo には一切乗らない。
- **送信**: `Net.sendSelectionIfChanged()`。`state.selection` は数十箇所で直接 mutate
  される Set のため、全 mutation 箇所への配線は漏れを量産する。代わりに **`frame()`
  (rAF ドライバ)から draw 後に1回呼び、直列化キー(`ids.join(',')`)が前回送信時と
  変わったときだけ送る**。選択変更は必ず `invalidate()` を伴う(選択は描画対象のため)
  ので、この1箇所で undo/redo・リモート op 起因の選択復元を含む全経路を捕捉できる。
- **スロットルは不要**: 送信は「フレームあたり最大1回 × 変化時のみ」に構造的に制限
  される(カーソルの `CURSOR_THROTTLE_MS` は pointermove が数百 Hz で発火するための
  対策であり、こちらには同じ問題が存在しない)。
- **新規ピア参加時の再送**: `_touchPeer` が新規ピアを登録したとき `_lastSelSent` を
  リセットし `invalidate()` する — 参加直後のピアにも現在の選択が1フレーム以内に届く
  (カーソルには無い配慮。カーソルは動かせば直ちに再配信されるが、選択は次に変更される
  まで配信されないため)。
- **受信検証**: `Array.isArray(msg.ids)` を確認し、文字列要素のみを `MAX_OP_SHAPES`
  件まで採用(防御的 intake、ADR-0010 の有限数チェックと同じ精神)。
- **WebRTC ピア識別**: ADR-0010 で発見した `_rtcPeerId` の落とし穴をそのまま踏襲 —
  `case 'selection'` も `viaRtc ? this._rtcPeerId : msg.peer` でエントリを解決する。

### FT-12 の3論点への回答

- **(a) 自分の選択色との区別**: ピア選択は該当図形の bbox に**そのピアの
  `PEER_COLORS` 色・細線 (1px)・破線 [3,3]** の外枠のみ。自分の選択(
  `--accent-contrast` 実線 1.5px + ハンドル)とは色・線種・ハンドル有無の3点で区別
  される。ロック選択の破線 [5,4] ともパターンが異なる。
- **(b) 複数ピア・複数選択時の描画量**: ハンドル・ラベルは描かず bbox 外枠のみ。
  ピアごとに1回のループ、図形解決は `byId()`(ADR-0009 で O(1))。同じ図形を複数ピアが
  選択した場合は外枠が重なって描かれる(各ピアの色が 1px 破線で重なるだけで破綻しない
  ため、重複排除はしない)。
- **(c) ロック済み図形も対象**: 対象とする。選択とロックは独立した状態であり、
  ロック中でも「誰かがこの図形に注目している」ことを示す価値がある(受信側で
  `locked` を見て間引く根拠がない)。

### レンダリング

`draw()` のオーバーレイパス(CSS-px 空間、DPR はトランスフォームが供給 — 本バージョンで
修正した HiDPI 二重掛けの教訓に従い `G.w2s` の出力をそのまま使う)に
`drawPeerSelections()` を追加し、`drawPeerCursors()` の直前に呼ぶ(枠の上にカーソルが
乗る方が視覚的に自然)。ADR-0010 と同じく `Presentation.isActive()` 中は非表示。

## 代替案 (Alternatives)

- **全 mutation 箇所に送信を配線**: 却下。`state.selection` の直接 mutate は 40 箇所超
  (undo/redo の `origSel` 復元含む)あり、漏れが構造的に避けられない。フレーム境界での
  変化検出は1箇所で全経路を覆う。
- **draw() 内から送信**: 却下。CLAUDE.md の不変条件「Render は `state` を読むのみ」に
  抵触する(ネットワーク送信は例外リスト入りに値しない副作用)。rAF ドライバの
  `frame()` は描画関数ではないため、そこに置く。
- **選択の重複排除(同一図形を複数ピアが選択したら1枠に統合)**: 却下(YAGNI)。
  破線の重なりは視覚的に破綻せず、統合は「どのピアの色を出すか」という新たな設計論点を
  生むだけ。
- **`{k:'cursor'}` メッセージに ids を同乗させる**: 却下。カーソルはスロットル付き
  高頻度、選択は変化時のみの低頻度で、送信条件が異なる。混ぜると両方の条件が濁る。

## 影響 (Consequences)

- `Net` に `_lastSelSent` フィールドと `sendSelectionIfChanged()` メソッド、
  `_onRecv` に `case 'selection'` 追加。`_touchPeer` の新規ピア分岐に再送トリガ追加。
- `state.peers` の値に任意の `sel:string[]` フィールドが増える(ピア reap で自然消滅)。
- 新規関数 `drawPeerSelections()`、`draw()` から1行、`frame()` から1行の呼び出し追加。
- テスト: 2-peer 収束ハーネス(ADR-0010 と同一パターン)で (a) BC 経路で選択 ids が
  相手の `peers.get(...).sel` に入る、(b) `viaRtc=true` は `_rtcPeerId` に紐づく、
  (c) 配列でない/文字列でない ids は拒否・除外される、(d) 変化が無ければ再送しない・
  変化すれば送る(`sendSelectionIfChanged` のキー比較)、(e) 新規ピア参加で
  `_lastSelSent` がリセットされる、を固定。
